# ImioCode 第五章：Prompt 工程体系 Spec

## 背景

ImioCode 已具备统一的 LLM 流式调用、工具系统和 Agent Loop，但当前 Prompt 信息缺少统一组织规则：

- 身份、行为、安全、工具用法等内容没有清晰的模块边界。
- 环境信息和 Plan Mode 指令可能进入 System Prompt，导致稳定前缀变化，降低 Prompt Cache 命中率。
- 不同 Provider 分别处理提醒消息和工具定义，行为容易产生差异。
- 六个核心工具的描述较简略，模型难以准确选择和组合工具。
- 缺少固定的人工评估场景，Prompt 调整后的效果无法稳定对比。

## 目标

- 建立由七个固定模块组成、按优先级稳定排序的 System Prompt。
- 建立统一组装管线，将稳定指令、动态消息和工具定义准确分发到三个 API 通道。
- 将环境上下文和 Plan Mode 指令通过独立的 `<system-reminder>` 用户消息注入。
- 根据 Provider 能力应用缓存策略，并通过 API usage 数据观测真实缓存命中。
- 强化六个工具的使用说明、优先关系和配合规则。
- 提供五个可重复执行的定性评估场景。
- 保持现有 Agent Loop、流式事件和多 Provider 能力兼容。

## 功能需求

- **F1：七模块 System Prompt**  
  System Prompt 必须由以下七个固定模块组成，并按稳定优先级排序：身份定义、行为准则、工具使用、代码质量、安全约束、任务模式、输出风格。模块为空时可省略，但其余模块顺序不得变化。

- **F2：统一的三通道组装管线**  
  每次 LLM 请求统一组装以下七类信息：System Prompt 模块、环境上下文、会话级提醒、历史消息、当前任务轨迹、轮次级提醒、工具定义。组装结果只能进入：
  - `system`：稳定的七模块 System Prompt。
  - `messages`：环境上下文、提醒、历史消息和当前任务轨迹。
  - `tools`：当前模式下允许模型调用的工具定义。

- **F3：环境上下文注入**  
  每个新用户任务开始时采集一次工作目录、操作系统、Shell、当前时间及时区、Git 分支和工作区状态。环境信息作为消息通道中的第一条独立用户提醒注入，在同一次 Agent Loop 中保持不变，下一个用户任务重新采集。环境信息不写入持久会话历史。

- **F4：提醒消息机制**  
  所有提醒均使用独立的用户消息，并以 `<system-reminder>...</system-reminder>` 包裹，不得拼接到 System Prompt 或用户原始文本中。消息逻辑顺序为：环境提醒、会话级提醒、历史消息、当前任务轨迹；轮次级提醒紧邻当前轮上下文。Provider 可以进行协议要求的消息归并，但不得改变提醒语义和顺序。

- **F5：Plan Mode 提醒改造**  
  正常执行模式不注入 Plan Mode 提醒。Plan Mode 的第 1、6、11……轮注入完整只读规划指令，其余轮次注入精简提醒。提醒不得进入 System Prompt，不得写入持久历史，并继续保证 Plan Mode 只向模型暴露只读工具。

- **F6：工具描述强化**  
  ReadFile、WriteFile、EditFile、Bash、Glob、Grep 的工具描述必须说明适用场景、使用限制、选择优先级及与其他工具的配合方式，使模型能够优先使用专用工具，避免不必要的命令执行和整文件覆盖。

- **F7：Provider 感知的缓存控制**  
  统一组装结果携带缓存意图：
  - 支持显式缓存控制的 Provider，为稳定的 System Prompt 和工具定义设置临时缓存标记。
  - 不支持该字段的 Provider 不发送非法参数，并通过稳定的内容和顺序利用其原生自动缓存。
  - 环境上下文、历史、任务轨迹和轮次提醒保持在动态消息通道，不能污染稳定缓存前缀。

- **F8：缓存使用量观测**  
  所有 Provider 返回的缓存读取量和缓存写入量必须统一映射到 usage 数据。相同稳定前缀的第二次真实请求应能通过非零缓存读取量识别命中；若受 Provider 最小长度或账户策略限制，必须保留真实 usage 并明确报告原因，不能伪造命中。

- **F9：五个定性评估场景**  
  提供可重复人工执行的五类场景：
  1. 项目探索：优先组合 Glob、Grep、ReadFile，避免滥用 Bash。
  2. 精确修改：先读取再修改，优先 EditFile，避免整文件覆盖。
  3. 创建文件：确认路径和上下文后使用 WriteFile，并验证结果。
  4. 失败恢复：根据命令错误调整方案，避免无变化地重复执行。
  5. Plan Mode：仅调查和输出计划，不执行写入或修改操作。

## 非功能需求

- **N1：稳定性**  
  相同配置和输入必须生成内容及顺序一致的 System Prompt、工具定义和提醒布局，避免无意义变化破坏缓存。

- **N2：兼容性**  
  保持 OpenAI、Anthropic、DeepSeek 三类 Provider 可用，不改变现有流式响应、工具调用、Agent 事件及会话历史的外部行为。

- **N3：可测试性**  
  Prompt 模块排序、三通道路由、提醒注入、Plan Mode 轮次策略、缓存字段序列化和 usage 解析均应能够通过自动化测试独立验证，不依赖真实模型才能完成基础测试。

- **N4：安全性**  
  环境上下文只包含完成任务所需的非敏感信息。不得注入环境变量值、访问令牌、API Key、Git 凭据或其他秘密数据。

- **N5：协议正确性**  
  每个 Provider 只接收其官方 API 支持的字段和消息结构。Provider 不支持显式缓存标记时，必须省略该字段。

- **N6：性能与成本**  
  Prompt 组装不能引入外部网络请求；环境信息每个用户任务最多采集一次。稳定内容应尽可能复用，以降低重复输入 Token 成本。

- **N7：可维护性**  
  Prompt 内容、信息路由和 Provider 序列化职责应分离。新增或调整一个 Prompt 模块时，不应要求同步修改所有 Provider。

- **N8：可观测性**  
  缓存读取、缓存写入、输入和输出 Token 数据应沿用统一 usage 模型，且能够在测试或诊断输出中查看。

## 不做的事

- 不加载或解析 `MEWCODE.md` 等项目级指令文件，留到第 7 章。
- 不实现自动记忆、长期记忆或跨会话记忆，留到第 9 章。
- 不接入真实 MCP Server，留到第 6 章。
- 不实现 LLM-as-judge、自动评分或自动 Prompt 优化，五个场景仅用于人工定性评估。
- 不新增权限确认流程、用户授权弹窗或危险操作审批。
- 不重构 Agent Loop 的停止条件、工具并发策略和事件模型。
- 不保证所有 Provider 都产生缓存命中；只保证请求结构正确、稳定前缀可缓存、usage 如实返回。
- 不把动态环境、Plan Mode 状态或轮次提醒写入 System Prompt。
- 不收集文件内容、环境变量值、凭据或其他敏感信息作为环境上下文。
- 不引入 Prompt 模板管理后台、远程配置中心或 Prompt 版本发布系统。

## 验收标准

- **AC1（对应 F1）**  
  使用乱序注册的七个 Prompt 模块组装请求，最终 System Prompt 始终按规定优先级输出；重复组装结果完全一致。

- **AC2（对应 F2）**  
  检查一次完整请求，七类信息分别进入规定的 system、messages、tools 通道，没有环境信息或提醒混入 System Prompt，也没有工具定义混入消息。

- **AC3（对应 F3）**  
  启动一个多轮工具任务，环境提醒只采集一次且各轮内容一致；发起下一个用户任务时环境重新采集。提醒包含规定字段但不包含环境变量值或凭据。

- **AC4（对应 F4）**  
  同时提供环境提醒、会话级提醒和轮次级提醒时，每项均为独立的用户消息并带完整 XML 标签；请求中的语义顺序符合约定，用户原始输入保持不变。

- **AC5（对应 F5）**  
  在 Plan Mode 连续运行至少六轮：第 1、6 轮出现完整规划提醒，第 2～5 轮出现精简提醒，System Prompt 保持不变，并且模型请求中只暴露只读工具。切换到正常模式后不再出现 Plan Mode 提醒。

- **AC6（对应 F6）**  
  检查六个工具定义，每个描述均包含适用场景、限制、优先选择原则或配合关系；五个评估场景中，模型能够按描述选择预期工具。

- **AC7（对应 F7）**  
  对三类 Provider 检查实际请求结构：支持显式缓存控制的请求在稳定 System Prompt 和工具定义上带临时缓存标记；不支持的请求不含非法字段；动态消息变化不改变稳定前缀。

- **AC8（对应 F8）**  
  三类 Provider 的缓存 usage 样例均能正确转换为统一的缓存读取量和写入量。当前已配置 Provider 连续发送两次稳定前缀相同的真实请求，第二次统一 usage 中的缓存读取量大于零即判定真实命中。

- **AC9（对应 F8）**  
  若真实 Provider 因最小前缀长度、账户能力或服务策略未命中，测试必须展示其真实 usage、请求稳定性证据和具体阻塞原因，该项记录为受外部条件限制，不能用模拟数据替代真实命中结果。

- **AC10（对应 F9）**  
  项目提供五个可单独执行的人工评估场景，每个场景包含输入、观察重点和预期工具行为，执行者能够按统一模板记录结果。

- **AC11（对应 F1～F8）**  
  自动化测试覆盖模块排序、三通道路由、提醒包装与顺序、环境刷新边界、Plan Mode 轮次、工具描述、Provider 缓存字段及 usage 解析，并全部通过。

- **AC12（对应 F2、F4、F5）**  
  现有 Agent 多轮工具调用、流式文本输出、工具结果回传和会话历史测试继续通过，没有因 Prompt 重构产生回归。

- **AC13（对应 F9）**  
  使用 tmux 启动 ImioCode，至少实际执行一个普通工具任务和一个 Plan Mode 任务；终端能够正常展示流式回复与工具调用，行为符合对应评估场景。
