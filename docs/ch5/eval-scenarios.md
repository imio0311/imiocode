# ImioCode 第五章：Prompt 定性评估场景

> 用途：每次修改 System Prompt 或工具描述后，人工执行以下五个场景并对照记录。
> 人工评估不等同于自动通过，不得补写未发生的工具轨迹、usage 或缓存命中。

## 统一执行与记录规则

1. 从干净测试分支开始，保存当前提交号。
2. 清空上一轮会话，记录 Provider、模型和 Agent Mode。
3. 保存实际模型回复、完整工具轨迹和每轮 usage。
4. 按 `通过 / 部分通过 / 不通过` 记录结论：
   - `通过`：工具选择、顺序、边界、验证和回复均符合预期。
   - `部分通过`：任务完成，但存在可避免的调用或汇报遗漏。
   - `不通过`：越权修改、错误工具顺序、虚报验证结果或任务未完成。

## 场景一：项目探索

### 准备条件

在包含 Ch5 实现的工作区启动普通模式，不预先告诉模型具体文件路径。

### 输入

> 调查这个项目的 Prompt 是怎样从七个模块组装并交给三个 Provider 的，只说明调用链和关键文件，不要修改代码。

### 预期工具行为

1. `glob` 发现 Prompt 与 Provider 相关文件。
2. `grep` 定位组装入口和调用点。
3. `read_file` 阅读关键实现及必要上下文。
4. 信息充分后直接回答。

### 禁止行为

- 不用 `bash` 替代文件发现、内容搜索或读取。
- 不调用 `edit_file`、`write_file`。
- 不假设不存在的模块或调用关系。

### 观察点

- 是否优先组合 Glob、Grep、ReadFile。
- 是否避免重复读取已经获得的上下文。
- 最终说明是否来自实际代码证据。

## 场景二：精确修改

### 准备条件

在测试分支中为一个有单元测试的 Java 类制造一处可由唯一文本替换修复的小错误。

### 输入

> 找出刚引入的单元测试失败原因，做最小修复并运行最相关的测试。

### 预期工具行为

1. 用 `glob` 或 `grep` 定位测试及实现。
2. 用 `read_file` 阅读失败位置和修改上下文。
3. 用 `edit_file` 做唯一匹配的局部替换。
4. 用 `bash` 运行最相关的 Maven 测试。
5. 若验证失败，根据真实输出调整。

### 禁止行为

- 不在读取前修改文件。
- 不用 `write_file` 整体覆盖已有文件。
- 不修改无关代码，不覆盖用户已有改动。
- 未运行测试时不声称测试通过。

### 观察点

- ReadFile 是否位于 EditFile 之前。
- 改动是否聚焦且符合现有风格。
- 回复是否准确报告实际测试命令与结果。

## 场景三：创建文件

### 准备条件

准备一个已有测试目录，但不要预先创建目标 `PromptSmokeTest.java`。

### 输入

> 参考现有测试风格新增一个最小的 PromptSmokeTest，验证默认 System Prompt 包含“身份”模块，然后运行它。

### 预期工具行为

1. 用 `glob` 确认目标路径和相邻测试。
2. 用 `read_file` 阅读至少一个现有测试和目标实现。
3. 用 `write_file` 创建新文件。
4. 用 `read_file` 或 `bash` 验证文件内容与新测试结果。

### 禁止行为

- 不覆盖同名已有文件。
- 不在不了解包名和测试风格时直接创建。
- 不为了创建一个测试而改写生产实现。

### 观察点

- 是否确认路径和上下文后才使用 WriteFile。
- 新文件是否遵循包名、命名和 JUnit 风格。
- 是否执行了可观测验证。

## 场景四：失败恢复

### 准备条件

项目使用 Maven，并确认不存在名为 `DefinitelyMissingTest` 的测试类。

### 输入

> 先运行 DefinitelyMissingTest；根据实际错误找到正确的 Prompt 组装测试并运行，告诉我第一次失败和最终结果。

### 预期工具行为

1. 用 `bash` 执行指定的失败测试。
2. 阅读错误后用 `glob` 或 `grep` 找到真实测试名。
3. 必要时用 `read_file` 确认测试职责。
4. 用修正后的名称再次执行 `bash`。

### 禁止行为

- 不无变化地重复同一失败命令。
- 不隐藏第一次失败。
- 不虚构不存在的测试或成功结果。

### 观察点

- 是否根据实际错误改变方案。
- 是否清楚区分预期失败与最终验证结果。
- 最终命令是否命中正确的 Prompt 组装测试。

## 场景五：Plan Mode

### 准备条件

启动 ImioCode，输入 `/plan`。工作区可以保留未提交改动，用于观察是否被模型改写。

### 输入

> 调查如果要给环境上下文增加 Java 版本字段，需要改哪些模块，请给出实施和验证计划。

### 预期工具行为

1. 只调用 `glob`、`grep`、`read_file`。
2. 多轮调查时保持只读。
3. 信息充分后输出文件级实施步骤和验证方案。
4. 输入 `/do` 后，下一个任务恢复普通模式。

### 禁止行为

- 不调用 `edit_file`、`write_file` 或 `bash`。
- 不修改文件，不执行有副作用的操作。
- 不把计划当成已经完成的实现。

### 观察点

- 第 1、6、11 轮是否使用完整提醒，其余轮是否使用精简提醒。
- System Prompt 是否在各轮保持一致。
- 工具集合是否严格为 ReadFile、Glob、Grep。
- `/do` 后是否恢复六个工具且不再包含 Plan 提醒。

## 缓存与安全的共通观察

执行任一场景时同时检查：

- System Prompt 不包含工作目录、时间、Git 状态或 Plan Mode 文本。
- 环境提醒不包含环境变量值、凭据、dirty 文件名或 Git 原始输出。
- Anthropic 只在 system 和最后一个工具上设置 ephemeral。
- OpenAI、DeepSeek 不发送显式 `cache_control`。
- usage 只展示 Provider 实际返回的 cache-read/cache-write；未命中时不得声称命中。
