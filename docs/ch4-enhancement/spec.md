# ImioCode Ch4 Agent Loop 增强 Spec

## 背景

ImioCode 已具备多轮 Agent Loop、统一事件流、工具分批执行、五种终态和 Plan Mode。当前模型流必须完整结束后才开始执行工具；模型请求失败会直接结束任务；连续请求不存在的工具名只能依赖轮数上限停止。

这会带来三个问题：

- 多个只读工具无法与仍在进行的模型流重叠执行。
- 临时网络、限流及输出 token 不足会中断整个任务。
- 模型持续生成未知工具名时会浪费循环预算。

## 目标

- 完整只读工具调用一旦解析完成即可提前执行，同时保持工具顺序和安全屏障。
- 在尚未启动工具时，对可恢复的模型错误自动重试。
- 重试过程可通过统一事件流观察，旧的半截输出与新尝试明确分隔。
- 输出 token 不足时逐步提高单次请求上限，最高 64000。
- 连续三次请求未知工具时触发独立熔断终态。
- 保持现有 Plan Mode、任务超时、历史事务和 Provider 抽象不变。

## 功能需求

- F1：模型流产生完整工具调用后，系统应立即识别其原始索引、工具名称和风险级别。
- F2：流尚未结束时，只允许已完整解析、已启用、当前模式允许且风险为 LOW 的工具提前执行。
- F3：WriteFile、EditFile、Bash 等非 LOW 工具只能排队；模型流正常完成后，等待此前只读工具完成，再按原始顺序串行执行。
- F4：Provider 交错返回多个工具调用时，应按原始索引调度；后续工具不得越过尚未完成的顺序屏障。
- F5：只读工具可以与模型流重叠执行，但返回模型的结果顺序必须与工具调用原始顺序一致。
- F6：模型流失败时，如果尚未启动任何工具，可根据错误类型自动重试；一旦任一工具开始执行，本轮不得自动重试。
- F7：限流、网络错误、服务端错误和单次请求超时属于可重试错误；认证失败、模型不存在、协议错误和未知错误不得自动重试。
- F8：每轮模型请求在首次失败后最多重试三次。限流优先遵守 Retry-After；没有 Retry-After 时，以及网络、服务端和请求超时错误，依次等待 1 秒、2 秒、4 秒。
- F9：重试等待不得超过任务剩余时间；用户取消或任务超时时，应立即终止等待和后续尝试。
- F10：每次重试都应发布包含轮次、尝试次数、错误类别和等待时间的重试事件。
- F11：失败尝试已输出的半截文本和 Thinking 保留在终端，并用重试提示与下一次尝试分隔；失败尝试不得写入会话历史。
- F12：模型因输出 token 上限结束时，应提高当前轮请求的输出上限并立即重试；每次翻倍，最高不超过 64000，并计入同一组三次重试预算。
- F13：达到 64000 后仍因输出 token 上限失败，应按模型错误结束任务，不得无限重试。
- F14：按工具调用原始顺序统计未知工具。只有注册中心不存在的工具名计数；识别到任一已注册、已启用且当前模式允许的工具后，连续计数清零。
- F15：已禁用工具以及 Plan Mode 禁止的工具不计入未知工具次数，也不负责清零。
- F16：连续第三次请求未知工具后，应立即进入独立的“未知工具过多”停止状态，不再启动后续工具或请求模型。
- F17：未知工具熔断应发布可区分的停止事件，终端显示明确原因；未完成轨迹不进入正式历史。
- F18：自动重试只针对模型请求，不自动重试失败工具，也不回滚已经发生的工具副作用。
- F19：OpenAI、Anthropic 和 DeepSeek 应把输出 token 上限、限流和其他可恢复错误归一为一致行为。
- F20：现有任务总超时、最大轮数、并发上限、Plan Mode 和取消行为在增强后继续生效。

## 非功能需求

- N1：流式调度、工具完成和取消存在并发竞争时，每个工具最多执行一次。
- N2：模型流事件可以交错到达，但相同输入下的工具调度顺序和结果排列必须确定。
- N3：提前执行只读工具不得突破现有安全工具最大并发数。
- N4：任何写入工具或命令工具都不得与其他非 LOW 工具并发，也不得越过前置批次。
- N5：重试次数、退避时间和输出 token 上限必须有固定边界，不得形成无限循环。
- N6：重试等待必须可取消，不得使用无法响应任务超时或用户中断的阻塞等待。
- N7：任务结束后不得遗留模型请求、重试定时任务、工具线程或子进程。
- N8：模型成功、停止、失败三种终态仍然互斥，每个任务只能发布一次最终状态。
- N9：已经发布到终端的失败尝试内容不得被误写入正式会话历史。
- N10：重试事件和错误提示不得暴露 API Key、认证头、Provider 原始响应、Thinking 签名或 encrypted content。
- N11：旧配置不增加新字段时仍能启动，并使用本章规定的固定重试策略。
- N12：现有六个工具的参数格式和调用名称保持不变。
- N13：三家 Provider 的原有正常流式文本、Thinking、工具解析和 Usage 行为不得回归。
- N14：自动化测试不得依赖真实模型服务或真实 API Key，应能确定性控制流事件、错误、时间和工具完成顺序。
- N15：必须覆盖流失败与工具启动、任务超时与重试、工具完成与熔断之间的竞争条件。
- N16：项目应保持干净编译、测试和打包，Ch2、Ch3 及原 Ch4 测试继续通过。
- N17：终端在富模式和 dumb 模式下都应清楚显示重试分隔与未知工具熔断原因。
- N18：真实端到端验收继续遵循 tmux 要求；环境不可用时必须记录实际阻塞，不得伪造通过。

## 不做的事

- 不实现上下文压缩、自动摘要或 ContextTooLong 恢复。
- 不增加压缩事件或压缩管理组件。
- 不实现权限系统、危险工具确认或用户审批界面。
- 不增加 AskUser、Hook、ToolNameFilter 等后续章节能力。
- 不允许 WriteFile、EditFile 或 Bash 在模型流结束前执行。
- 不在任何工具已经启动后自动重试模型流。
- 不自动重试失败工具。
- 不对已经执行的工具进行事务回滚。
- 不把重试次数、退避间隔或 64000 token 上限开放为配置项。
- 不自动清除终端中失败尝试已经显示的半截内容。
- 不改变 Plan Mode 生成计划后必须由用户输入 `/do` 才能执行的规则。
- 不实现跨用户任务的后台重试或恢复。
- 不新增核心工具或改变现有工具参数协议。

## 验收标准

- AC1：模型流尚未结束时完成两个 LOW 工具调用，观察到两个工具已开始执行，并且并发数不超过配置上限。
- AC2：流中先完成 LOW 工具、再完成 WriteFile、最后完成另一个 LOW 工具；观察到写工具等待流正常结束及前置 LOW 工具完成，后置 LOW 工具等待写工具完成。
- AC3：Provider 以乱序事件完成工具调用，最终每个工具只执行一次，结果按原始索引回传模型。
- AC4：模型流在任何工具开始前返回网络错误，系统依次重试，成功尝试进入下一阶段。
- AC5：模型流在 LOW 工具已经开始后断开，系统不再重试，取消活动工具并以错误结束。
- AC6：限流错误携带 Retry-After 时按该时间等待；未携带时采用 1/2/4 秒退避。
- AC7：网络、服务端和请求超时错误最多重试三次；第四次失败后产生唯一失败终态。
- AC8：认证、模型不存在、协议和未知错误第一次发生后立即结束，不发布重试事件。
- AC9：重试等待期间触发用户取消或任务超时，等待立即结束，不再发起模型请求。
- AC10：每次重试前都能观察到包含轮次、尝试编号、错误类型和等待时间的重试事件。
- AC11：第一次尝试流出部分文本后失败，终端保留半截文本并显示重试分隔；成功尝试单独显示，历史只包含成功响应。
- AC12：模型连续返回输出 token 上限时，请求上限逐次翻倍但不超过 64000；成功后继续当前 Agent 任务。
- AC13：输出上限达到 64000 后仍失败，任务停止且没有无限请求。
- AC14：按顺序请求两个未知工具、一个有效工具、再三个未知工具；前两个计数被有效工具清零，后三个触发熔断。
- AC15：Plan Mode 中连续请求 WriteFile 或已禁用工具不会触发未知工具熔断，也不会实际执行。
- AC16：第三个连续未知工具出现后，不执行同一响应中的后续工具，也不开始下一轮模型请求。
- AC17：未知工具熔断产生独立停止原因和一次停止事件，终端显示明确说明，正式历史保持不变。
- AC18：成功多轮任务仍原子提交完整轨迹；重试耗尽、熔断、超时和取消均不提交未完成轨迹。
- AC19：OpenAI、Anthropic 和 DeepSeek 模拟流分别通过限流、网络、输出 token 上限及正常工具调用回归测试。
- AC20：取消和流失败竞争、工具完成和流失败竞争时，不重复执行工具、不重复发布终态、不遗留活动任务。
- AC21：完整测试和打包通过，原 Ch2、Ch3、Ch4 测试无新增失败。
- AC22：真实程序启动后能观察重试提示、提前执行的只读工具、未知工具熔断和正常退出；若 tmux 环境不可用，验收记录包含真实阻塞证据。
