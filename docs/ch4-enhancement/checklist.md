# ImioCode Ch4 Agent Loop 增强 Checklist

> 每项都必须通过运行测试、启动程序或观察事件来验证。验收时记录实际命令、结果和证据；环境不可用时记录真实阻塞，不把预期结果当作通过。

## 流式工具调度

- [ ] AC1：模型流尚未结束时，两个完整 LOW 工具已经开始执行，且同时运行数不超过配置上限。（验证：运行 `mvn -q -Dtest=StreamingToolSchedulerTest test` 中双 LOW 闩锁场景；在允许模型流结束前，观察两个工具的启动信号和记录的最大并发数。）
- [ ] AC2：LOW → WriteFile → LOW 的调用严格遵守屏障，WriteFile 等待流成功和前置 LOW 完成，后置 LOW 等待 WriteFile 完成。（验证：运行调度器屏障测试；对照记录的 `low-0-start/end → write-start/end → low-2-start/end` 顺序。）
- [ ] AC3：工具完成事件乱序时，每个工具只执行一次，回传结果仍按原始索引排列。（验证：先提交 index 1、再提交 index 0，重复提交一个索引；运行测试并核对调用次数均为 1、结果顺序为 0、1，重复索引产生协议错误。）
- [ ] S1：流正常结束前，WriteFile、EditFile 和 Bash 均不会开始执行。（验证：分别提交三类完整调用，在释放流结束闩锁前断言执行计数为 0；流结束后才观察到执行。）
- [ ] S2：最大轮数的最后一轮即使模型请求工具，也不会提前或补执行该工具。（验证：运行 Agent 最大轮数场景，观察 `MAX_ITERATIONS` 停止原因和工具执行计数 0。）

## 模型重试与输出上限

- [ ] AC4：工具开始前发生 NETWORK 错误时会重试，后续成功尝试继续本轮任务。（验证：模拟首次网络失败、第二次成功；观察两次模型请求、一个重试事件，且只把成功响应加入轨迹。）
- [ ] AC5：LOW 工具开始后模型流断开时不再重试，活动工具被取消并以错误结束。（验证：用闩锁等待 LOW 启动后注入 NETWORK；观察模型请求次数为 1、工具收到取消、唯一终态为失败。）
- [ ] AC6：RATE_LIMIT 携带 Retry-After 时采用该值；未携带时依次采用 1、2、4 秒。（验证：使用虚拟等待器运行两组策略测试，核对记录的等待序列，不进行真实睡眠。）
- [ ] AC7：NETWORK、SERVER_ERROR 和 TIMEOUT 最多各重试三次，第四次失败后仅产生一次失败终态。（验证：对三类错误分别模拟连续四次失败，核对模型请求数 4、重试事件数 3、终态数 1。）
- [ ] AC8：AUTHENTICATION、MODEL_NOT_FOUND、PROTOCOL 和 UNKNOWN 首次发生后立即结束，不发布重试事件。（验证：参数化运行不可重试错误测试，核对每种错误的请求数为 1、重试事件数为 0。）
- [ ] AC9：重试等待期间取消或任务超时会立即结束等待，且不再请求模型。（验证：在可控制等待器进入等待后触发两种停止条件，要求测试在短超时内返回、请求数不增加、无活动等待任务。）
- [ ] AC10：每次重试前都发布轮次、下一尝试编号、错误类别、等待时间和当前输出上限，事件不包含 Provider 原始错误正文。（验证：捕获重试事件并逐字段核对；用带敏感标记的原始异常检查事件和终端输出均不含该标记。）
- [ ] AC11：失败尝试的半截文本保留在终端并与下一次尝试分行显示，但正式历史只包含成功尝试。（验证：首次输出部分文本后失败、第二次成功；检查富模式和 dumb 模式输出顺序，并检查会话历史不存在首次文本。）
- [ ] AC12：连续 OUTPUT_LIMIT 使请求上限逐次翻倍且不超过 64000，成功后继续当前 Agent 任务。（验证：从已知初始值模拟两次 OUTPUT_LIMIT 后成功，核对每次请求 JSON 的上限、零等待重试事件及最终完成状态。）
- [ ] AC13：请求上限已经达到 64000 后再次 OUTPUT_LIMIT 会停止，不产生相同上限重试或无限请求。（验证：模拟上限达到 64000 后继续失败，核对有限请求数、无额外重试决策和唯一失败终态。）

## 未知工具熔断

- [ ] AC14：两个 UNKNOWN 后遇到 AVAILABLE 工具会清零，再出现三个 UNKNOWN 时才熔断。（验证：按该顺序输入工具解析结果，观察前三个未知中的前两个不触发熔断，最后第三个连续未知返回 OPENED。）
- [ ] AC15：DISABLED 和 DISALLOWED 工具既不增加也不清零未知计数，Plan Mode 中 WriteFile 不执行且不触发熔断。（验证：在一个 UNKNOWN 前后插入禁用工具和 Plan Mode WriteFile，核对计数保持；连续多次 Plan Mode WriteFile 的执行计数和熔断数均为 0。）
- [ ] AC16：第三个连续 UNKNOWN 出现后立即取消模型流和活动 LOW，不执行同一响应后续工具，也不开始下一轮模型请求。（验证：模型流依次给出 LOW、三个 UNKNOWN、后续 LOW；核对活动 LOW 收到取消、后续 LOW 执行计数 0、模型请求数 1。）
- [ ] AC17：未知工具过多产生独立 `TOO_MANY_UNKNOWN_TOOLS` 停止原因和一次停止事件，终端显示明确中文说明。（验证：运行 Agent 与终端集成测试，核对停止原因、事件数及富模式/dumb 模式文本。）
- [ ] S3：失败并准备重试的半截模型尝试不会把未知计数重复提交；正常完成的尝试才提交计数。（验证：首次尝试观察 UNKNOWN 后网络失败、重试再次观察相同 UNKNOWN；确认任务级计数只增加一次。）

## 会话、取消与安全集成

- [ ] AC18：成功多轮任务原子提交完整用户、助手和工具轨迹；重试耗尽、熔断、超时和取消均不提交未完成轨迹。（验证：运行 `mvn -q -Dtest=ConversationSessionTest test`，逐个场景比较发送前后的历史快照。）
- [ ] AC20：取消与流失败、工具完成与流失败、工具完成与熔断发生竞争时，工具至多执行一次、任务只发布一个终态且没有活动任务遗留。（验证：连续三次运行 `mvn -q -Dtest=StreamingToolSchedulerTest,StreamingTurnExecutorTest,AgentCancellationTest,ConversationSessionTest test`，每次均核对调用次数、终态数和关闭状态。）
- [ ] I1：任务总超时优先于 Retry-After 和退避时间，不能因重试延长。（验证：任务剩余时间短于计划等待时运行测试，观察不进入等待且以 TIMEOUT 停止。）
- [ ] I2：自动重试只作用于模型请求，失败工具不会自动重跑，已发生的副作用不会被回滚。（验证：让写工具返回失败，核对执行次数为 1、后续模型行为沿用现有工具结果协议，文件副作用未被框架反向修改。）
- [ ] I3：现有六个核心工具名称、参数 Schema 和执行行为保持兼容。（验证：运行 `mvn -q -Dtest=ReadFileToolTest,WriteFileToolTest,EditFileToolTest,BashToolTest,GlobToolTest,GrepToolTest test`，期望全部通过。）
- [ ] I4：旧配置无需新增字段即可启动，重试时的请求级 token 上限不会写回全局配置或影响下一轮。（验证：运行配置和 Agent 测试；比较重试前后 `AppConfig` 及下一轮首个请求的上限。）
- [ ] I5：重试事件、错误提示和终端输出不包含 API Key、Authorization、Provider 原始响应、Thinking 签名或 encrypted content。（验证：用带唯一敏感标记的模拟输入运行事件与终端测试，再搜索捕获输出，期望标记不存在。）
- [ ] I6：正常模型流的文本、Thinking、工具调用、Usage 和取消在 OpenAI、Anthropic、DeepSeek 三种协议下均无回归。（验证：运行三家 ClientTest 与 RichEventTest，期望原有正常和富事件用例全部通过。）
- [ ] AC19：Provider 可恢复错误和输出上限具有统一行为。（验证：对三家模拟流分别注入限流、网络、输出上限和正常工具调用，观察统一错误分类和相同 Agent 重试结果。）
- [ ] I8：Plan Mode 仍只暴露读工具，必须由用户输入 `/do` 才恢复写入能力。（验证：运行 Plan Mode 集成测试，核对工具清单、模式提示和切换前后的 WriteFile 执行状态。）

## tmux 端到端场景

- [ ] AC22：真实程序的验收证据覆盖重试提示、提前执行 LOW 工具、未知工具熔断和正常退出；环境不可用时有真实阻塞记录。（验证：汇总 E1–E6 的 tmux pane、请求计数、进程状态或阻塞证据，四类目标缺一不可。）
- [ ] E1：在 tmux 中启动打包后的 ImioCode，发送要求查看项目结构的真实请求，观察模型流尚未结束时 ReadFile/Glob/Grep 等 LOW 工具开始执行，随后模型根据结果继续下一轮并给出最终回复。（验证：保存 tmux pane 输出，标注文本流、工具 queued/running/succeeded、下一轮和最终回答的实际顺序。）
- [ ] E2：在 tmux 中使用可控制模拟 Provider 让首次请求输出半截文本后返回可重试错误，观察半截文本保留、重试提示换行显示、第二次成功且会话可继续。（验证：保存 pane 输出和模拟服务请求计数，核对失败尝试未进入下一次请求历史。）
- [ ] E3：在 tmux 中使用可控制模拟 Provider 连续请求三个不存在的工具，观察独立熔断提示、无第四个工具执行、无下一轮模型请求，随后程序可以正常退出。（验证：保存 pane 输出、工具执行计数和模型请求计数。）
- [ ] E4：在 tmux 中输入 `/plan`，观察写工具不执行；输入 `/do` 后恢复正常模式并完成一次真实多轮工具任务。（验证：保存模式切换提示、工具事件和最终回复。）
- [ ] E5：在 tmux 中发起执行中的任务后发送 Ctrl+C，观察模型请求、等待和活动工具被取消，终端只显示一个停止结果且进程无残留。（验证：保存 pane 输出并检查 tmux pane/相关进程状态。）
- [ ] E6：如果本机、WSL、tmux、真实 API 或模拟环境不可用，验收报告明确标记对应场景未通过或被阻塞，并附探测命令、退出码和错误文本。（验证：报告中的每个未执行场景都有可复现证据，不以推测替代实际结果。）
