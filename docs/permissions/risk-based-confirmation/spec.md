# 风险分级确认策略 Spec

## 背景

当前默认权限配置使用“逐次询问”模式。只读操作可以直接执行，但文件写入以及多数命令都会要求用户确认；同时，命令工具和未知的远程工具通常被整体标记为高风险。这导致构建、测试、格式化和常规文件修改也频繁中断 Agent，确认成本过高，并且固定风险标签不能准确反映一次具体操作的真实危险程度。

## 目标

- 默认交互下，常规读取、项目内文件编辑和普通本地开发命令无需确认。
- 根据每次调用的实际参数动态判定命令风险，而不是把整个命令工具固定视为高风险。
- 高风险但仍可恢复或有明确用户意图的操作进入确认流程。
- 已知不可逆的系统破坏命令继续硬拦截，不能通过模式或规则绕过。
- 无法可靠判断副作用的 MCP 或第三方工具保持保守，默认要求确认。

## 功能需求

- F1：保留五种现有权限模式；将自动编辑模式调整为风险驱动行为，并作为未显式配置权限模式时的默认模式。逐次询问、只读、完全信任和锁定模式继续保留各自语义。
- F2：读取操作在自动编辑模式下直接执行；通过路径沙箱校验的项目内写入操作在自动编辑模式下直接执行。
- F3：命令操作必须结合命令内容动态分级。构建、测试、格式化、代码搜索、状态查询和普通本地开发命令归为低或中风险并自动执行。
- F4：删除或覆盖数据、向远程 Git 仓库写入、改写 Git 历史、发布软件包、全局安装、修改权限或系统配置、执行远程脚本等操作归为高风险并要求用户确认。
- F5：复合命令按最高风险决定；任一片段命中危险命令黑名单时整体拒绝，任一片段为高风险时整体确认，其余片段才允许自动执行。
- F6：现有危险命令黑名单和路径沙箱仍位于权限链最前方，任何权限模式和允许规则都不能绕过硬拦截或沙箱拒绝。
- F7：显式的拒绝和询问规则优先于自动风险决策；用户配置的精确允许规则可以放行对应的高风险或未知工具，表示用户已主动建立信任；强制覆盖 Skill 的专用安全兜底除外。
- F8：MCP、Skill 专属工具和其他无法可靠判断副作用的第三方工具默认按高风险处理；只有工具提供可信风险元信息或命中显式允许规则时才可免确认。
- F9：强制覆盖远程 Skill 继续按高风险处理；除完全信任模式外始终确认，精确允许规则也不能绕过此专用安全兜底。
- F10：确认界面必须展示工具名、动态风险等级、脱敏后的目标和判定原因，让用户知道为什么被询问。
- F11：当前项目配置和配置示例采用自动编辑模式，使正常启动后的默认体验成为“普通操作自动执行、高风险操作确认”。

## 非功能需求

- N1：风险判断必须确定、可测试；相同命令和配置应得到相同结果。
- N2：风险判断失败时采用保守策略，返回确认或拒绝，不能静默放行。
- N3：错误、日志和确认信息不得暴露 API Key、令牌或完整敏感参数。
- N4：风险检查不得执行待判断命令，也不得发起网络请求。
- N5：已有权限规则文件、五种模式名称和 Slash Command 用法保持兼容。
- N6：权限判断的额外延迟应不可感知，不引入外部依赖或模型调用。

## 不做的事

- 不新增第六种权限模式。
- 不改变 HITL 对话框的交互按键和阻塞唤醒机制。
- 不为 MCP 协议扩展新的风险元数据标准。
- 不实现网络请求限制、资源配额或审计日志。
- 不允许模型自行修改权限模式或自动生成永久允许规则。

## 验收标准

- AC1：未配置权限模式时进入自动编辑模式；显式选择其他模式时仍按原模式工作。
- AC2：读取、项目内写文件、改文件无需确认；路径逃逸仍直接拒绝。
- AC3：构建、测试、格式化、搜索和状态查询命令无需确认。
- AC4：删除/覆盖、Git 推送或历史改写、发布、全局安装、权限/系统修改和远程脚本触发确认。
- AC5：危险命令即使在完全信任模式或存在允许规则时仍直接拒绝。
- AC6：复合命令遵守“拒绝优先，其次最高风险”的聚合规则。
- AC7：未知 MCP/第三方工具默认确认；精确允许规则可放行，拒绝规则仍可拦截。
- AC8：确认提示显示动态风险等级和脱敏原因，不包含密钥或令牌。
- AC9：逐次询问、只读、完全信任、锁定模式及已有规则加载测试无回归。
- AC10：Java 21 全量测试、打包和真实终端端到端场景全部通过。
